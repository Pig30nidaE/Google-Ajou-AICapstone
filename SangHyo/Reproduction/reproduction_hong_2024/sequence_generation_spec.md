# 시퀀스 생성 명세

구현: `src/sequences/builder.py`. 계약 테스트: `tests/test_sequence_boundary.py`,
`tests/test_sequence_raw_row_overlap.py`.

---

## 0. 핵심 규칙

> **시퀀스는 이미 결정된 split의 한쪽 안에서만 만든다.**

`build_sequences(frame, ...)`는 이미 한쪽으로 제한된 프레임을 받는다. 입력 안에
경계가 없으므로 경계를 넘는 윈도우가 **생길 수 없다.** "만든 뒤 걸러내는" 방식이
아니라 "만들어질 수 없게 하는" 방식이다.

유일한 예외는 `build_sequences_literal()`이며, 논문 문언 그대로의 순서를 재현해
누수 크기를 **측정**하기 위한 것이다. `leakage_diagnostic_only=True` 없이는
`ValueError`를 던진다.

## 1. 절차

1. **피험자별 날짜 오름차순 정렬** — `groupby(subject_id)` 후 `sort_values(date)`.
2. **날짜 중복 처리** — 로더 단계에서 이미 (피험자, 날짜)당 1행으로 축약되어 있다.
   시퀀스 빌더는 중복이 남아 있으면 `ValueError`를 던진다(조용히 넘어가지 않는다).
3. **연속일 판정** — 인접 날짜 차가 정확히 1일인 구간(run)으로 분할한다.
   `consecutive_runs()`가 담당한다.
4. **윈도우 절단** — 각 run 안에서만 길이 L의 윈도우를 stride 간격으로 뽑는다.
   run 길이가 L 미만이면 아무것도 만들지 않는다.
5. **라벨 부여** — 해당 피험자의 진단 라벨(시간에 따라 변하지 않음).
6. **provenance 기록** — 아래 표의 모든 필드.

## 2. sequence 객체의 provenance

| 필드 | 내용 |
| --- | --- |
| `subject_id` | 출처 피험자 |
| `sequence_id` | `{split}\|L{길이}\|{피험자}\|{시작일}` |
| `start_date` / `end_date` | 윈도우의 첫날/마지막날 |
| `raw_dates` | 윈도우가 포함하는 원시 날짜 전체 (tuple) |
| `raw_row_ids` | 윈도우가 포함하는 원시 행 id 전체 (tuple) |
| `sequence_length` | 3 / 4 / 5 |
| `is_calendar_consecutive` | 실제로 연속인지 여부 |
| `split_name` | `train` / `test` / `outer_train` / `inner_valid` … |
| `outer_fold` / `inner_fold` | 중첩 CV에서의 위치 (없으면 `None`) |
| `y` | 시퀀스 라벨 |

`raw_row_ids`가 실제 그 행들의 값과 일치하는지도 테스트로 확인한다
(`test_row_ids_match_the_feature_values`).

## 3. 파라미터

| 항목 | 값 | 출처 |
| --- | --- | --- |
| sequence length | 3 / 4 / 5 | 논문 §4.1 |
| stride | 1 | **논문 미보고** (A-08) |
| 연속일 요구 | 필수 | **논문 미보고**, 이 저장소의 결정 |
| 라벨 | 피험자 진단 | 논문 §3.2 |

## 4. 연속일 요구가 만드는 차이 (실측)

174명 중 **162명**의 기록에 하루 이상의 공백이 있다(총 1,089건).

| 길이 | 연속일만 (채택) | 행 순서만 (공백 무시) | 공백을 건너뛴 비율 |
| ---: | ---: | ---: | ---: |
| 3일 | 9,862 | 11,823 | 16.6% |
| 4일 | 8,972 | 11,649 | 23.0% |
| 5일 | 8,192 | 11,475 | 28.6% |

5일 윈도우의 **28.6%**가 실제로는 연속이 아니다. 이 윈도우들은 LSTM에 "연속 5일의
변화"로 제시되지만 실제로는 며칠이 비어 있다. `require_consecutive: false`로 재현할
수 있으나 기본값은 `true`다.

## 5. split별 시퀀스 수 (실측, stride=1, 연속일 요구)

### 실험 A / B1 — 피험자별 마지막 1주일 분할

| 길이 | train | test | test에서 평가 가능한 피험자 |
| ---: | ---: | ---: | --- |
| 3일 | 9,028 | 590 | 156 / 174 |
| 4일 | 8,212 | 426 | 132 / 174 |
| 5일 | 7,494 | 294 | **111 / 174** |

B1은 embargo(L-1일)와 validation(14일) 때문에 train이 더 줄어든다:
6,947 / 6,180 / 5,513.

> **주의:** 5일에서는 174명 중 111명만 test 시퀀스를 만들 수 있다. 마지막 1주일
> 안에 연속 5일이 없는 사람이 63명이다. 피험자 단위 지표의 분모가 174가 아니라는
> 사실을 반드시 함께 보고해야 한다. `thin_subjects` 블록이 이 값을 매번 기록한다.

### 실험 B2 / C — 피험자 분할 (5-fold의 첫 fold 기준)

| 길이 | outer train | outer test | train 피험자 | test 피험자 |
| ---: | ---: | ---: | ---: | ---: |
| 3일 | 7,925 | 1,937 | 139 | 35 |
| 4일 | 7,222 | 1,750 | 139 | 35 |

## 6. 시퀀스 단위 클래스 불균형

전체 5일 시퀀스: 음성 5,262 / 양성 2,930 (비율 1.80:1). 피험자 단위 111:63과 비슷한
비율이므로, 시퀀스 수가 특정 클래스에 심하게 쏠려 있지는 않다.

피험자당 5일 시퀀스 수는 **최소 2개, 중앙값 46개, 최대 118개**다. 이 편차가
undersampling 전략(A-07)과 피험자 단위 평가(A-19)를 필요하게 만든 이유다.

## 7. 같은 split 안의 윈도우 중첩은 누수가 아니다

stride=1이면 이웃한 윈도우가 L-1일을 공유한다. 이것은 정상이며 논문도 마찬가지다.
문제는 **split을 가로지르는** 공유뿐이다.

| 상황 | 판정 |
| --- | --- |
| train 윈도우끼리 날짜 공유 | 정상 |
| test 윈도우끼리 날짜 공유 | 정상 |
| train 윈도우와 test 윈도우가 같은 (피험자, 날짜) 공유 | **누수. 즉시 중단** |
| train과 test에 완전히 동일한 특징 윈도우 존재 | **누수. 즉시 중단** |

## 8. `paper_literal_variant` — 논문 문언 그대로의 순서

§4.2를 문자 그대로 읽으면 시퀀스가 분할보다 먼저 존재한다. 이때의 실측 누수:

| 길이 | 전체 윈도우 | 경계 교차 | 공백 포함 | **train과 공유되는 test 날짜** |
| ---: | ---: | ---: | ---: | --- |
| 3일 | 11,823 | 345 (2.9%) | 16.6% | 338 / 1,036 (**32.6%**) |
| 4일 | 11,649 | 514 (4.4%) | 23.0% | 492 / 1,021 (**48.2%**) |
| 5일 | 11,475 | 678 (5.9%) | 28.6% | 604 / 969 (**62.3%**) |

경계를 교차하는 윈도우 자체는 5.9%로 작아 보이지만, 그 윈도우들이 test 날짜를
train으로 끌고 들어가기 때문에 **5일에서는 test 날짜의 62.3%가 이미 train에서
관측된다.** 윈도우 비율만 보고 "영향이 작다"고 판단하면 안 되는 이유다.

이 수치는 논문 저자가 실제로 이 순서로 구현했다는 증거가 아니다. 논문의 서술
순서를 그대로 따랐을 때 **발생할 수 있는** 누수의 크기다.
